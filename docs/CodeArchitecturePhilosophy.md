# PROJECT-MA 코드 구조 철학

핵심 원칙은 다음 한 문장으로 정리한다.

> 사용처는 한 줄로 의도를 말하고, 그 기능의 객체가 내부 판단부터 실행까지 닫으며, 문제가 생기면 이름을 따라 한곳만 찾아가서 고칠 수 있어야 한다.

## 원칙

1. 사용 측은 의미만 말한다.
   호출자가 사전 검사, 타입 분기, 권한 처리와 예외 규칙까지 알아서는 안 된다.

2. 기능의 주인이 전체 책임을 가진다.
   기능의 상태, 정책, 검증과 실행은 해당 기능의 이름을 가진 객체 안에서 끝나야 한다.

3. 수정할 때 한곳만 보면 된다.
   하나의 오류를 고치기 위해 여러 Manager, Action과 Addon을 모두 검색해야 한다면 책임이 퍼진 구조다.

4. 객체지향은 객체 수를 늘리는 것이 아니다.
   Factory, Processor, Context와 Registry는 호출 및 디버깅 경로를 실제로 줄일 때만 추가한다.

5. 다형성은 중앙 분기를 없앨 때만 사용한다.
   새 타입이 기존 Manager의 분기를 계속 수정하게 해서도 안 되고, 단순한 분기 하나 때문에 객체 계층을 증축해서도 안 된다.

6. 정책 분기는 없어지는 것이 아니라 주인에게 간다.
   아이템 정책은 Item에, 스택 정책은 Stack Action에 존재해야 한다.

7. 사용하지 않는 기능은 존재하지 않는 것처럼 작동한다.
   선택 기능이 없으면 관련 상태, 바인딩, 실행 비용과 책임도 없어야 한다.

8. 중복 제거보다 책임 경계가 우선이다.
   공통화는 사용 경로와 디버깅 경로를 모두 짧게 만들 때만 한다.

## 완성 기준

필요한 구조는 빠짐없이 있지만 필요하지 않은 구조는 붙어 있지 않은 상태를 완성으로 본다. 목업도 이 기준을 따른다. 최종 책임자가 아직 존재하지 않아 임시 연결이 필요한 경우에는 코드의 정확한 위치, 최종 책임자와 제거 조건을 버전 관리 문서에 기록한다.
